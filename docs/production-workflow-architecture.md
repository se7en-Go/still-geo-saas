## 🎯 设计概览

### 核心设计理念
生产级后端保活工作流采用**分阶段容错架构**，确保在Render免费服务的限制下提供最大可用性。

### 设计目标
- ✅ **99.9%可用性**：通过智能保活避免服务休眠
- ✅ **优雅降级**：部分失败不影响整体功能
- ✅ **智能监控**：详细的状态追踪和报告
- ✅ **资源优化**：避免GitHub Actions限制和滥用
- ✅ **维护简单**：单一工作流，易于理解和修改

### 关键特性
- 🔄 **5个独立阶段**：初始化→唤醒→验证→报告→清理
- 🧠 **智能重试**：指数退避 + 随机抖动
- 📊 **状态共享**：跨阶段传递执行信息
- 🎛️ **可配置策略**：标准/激进/最小化三种模式
- 🔍 **详细监控**：每个阶段的详细执行记录

## 🏗️ 架构原理

### 分阶段执行架构

```
┌─────────────────────────────────────────────────────────────┐
│                    GitHub Actions 工作流                    │
├─────────────────────────────────────────────────────────────┤
│  Stage 1: Initialize    🚀 初始化和状态检查                  │
│  Stage 2: WakeUp        🔥 智能唤醒服务                      │
│  Stage 3: Verification  🧪 功能验证                         │
│  Stage 4: Reporting     📊 状态报告                         │
│  Stage 5: Cleanup       🧹 清理和归档                       │
└─────────────────────────────────────────────────────────────┘
```

### 容错设计原则

1. **独立阶段**：每个阶段独立运行，单个阶段失败不影响其他阶段
2. **继续执行**：使用 `if: always()` 确保后续阶段继续执行
3. **状态持久化**：通过 outputs 在阶段间传递状态信息
4. **快速失败**：在阶段内快速检测问题，避免长时间等待

## 📋 工作流详解

### Stage 1: Initialize (🚀 初始化)

**目标**：设置执行环境并检查服务初始状态

**核心功能**：
- 📋 设置执行参数（策略、调试模式、执行ID）
- 🏥 执行快速健康检查（10-30秒）
- 💾 保存初始状态供后续阶段使用

**输出信息**：
```yaml
strategy: standard | aggressive | minimal
debug_mode: true | false
initial_status: healthy | cold | unknown
execution_id: keepalive-YYYYMMDD-HHMMSS-NNN
```

### Stage 2: WakeUp (🔥 智能唤醒)

**目标**：根据初始状态智能唤醒休眠服务

**核心功能**：
- 🎯 根据初始状态决定是否需要唤醒
- 🔄 多阶段唤醒策略（轻量级探测→健康检查→强力唤醒）
- ⏱️ 智能超时和重试机制
- 📊 实时状态追踪

**唤醒策略矩阵**：

| 策略 | 最大尝试 | 基础延迟 | 最大时间 | 适用场景 |
|------|----------|----------|----------|----------|
| Minimal | 3次 | 5秒 | 60秒 | 快速检查 |
| Standard | 5次 | 15秒 | 120秒 | 常规使用 |
| Aggressive | 8次 | 10秒 | 180秒 | 问题排查 |

**唤醒流程**：
```
轻量级探测 → 健康检查 → 强力唤醒 → 指数退避等待 → 下一轮尝试
```

### Stage 3: Verification (🧪 功能验证)

**目标**：验证关键功能端点是否正常工作

**测试矩阵**：
```yaml
基础连接测试:
  endpoint: /api/health
  method: GET
  expected: 200,404
  timeout: 30s

API根目录测试:
  endpoint: /api
  method: GET
  expected: 200,404
  timeout: 30s

登录端点测试:
  endpoint: /api/auth/login
  method: POST
  data: {email: "healthcheck@example.com", password: "test123"}
  expected: 200,401,400
  timeout: 30s
```

**容错机制**：
- `fail-fast: false`：单个测试失败不影响其他测试
- `continue-on-error: true`：测试失败继续执行后续步骤

### Stage 4: Reporting (📊 状态报告)

**目标**：生成详细的执行报告和状态汇总

**报告内容**：
- 📊 各阶段执行结果汇总
- 🎯 整体服务状态判断
- 🔗 相关访问链接
- 🚨 失败时的故障排除指南

**状态徽章生成**：
- ✅ 在线：绿色徽章
- ⚠️ 检查：橙色徽章
- ❌ 离线：红色徽章

### Stage 5: Cleanup (🧹 清理归档)

**目标**：归档执行记录并进行清理

**归档内容**：
- 📝 完整的执行记录（JSON格式）
- 📈 性能统计信息
- 🔗 GitHub Actions链接

## 🔄 智能重试策略

### 指数退避算法

```bash
# 计算延迟时间
DELAY = BASE_DELAY × (2 ^ (attempt - 1)) + RANDOM_JITTER

# 示例（基础延迟15秒）
# 第1次: 15 + (0-4) = 15-19秒
# 第2次: 30 + (0-4) = 30-34秒
# 第3次: 60 + (0-4) = 60-64秒
```

### 智能等待策略

**Render服务启动特性**：
- 首次唤醒：30-90秒冷启动
- 休眠唤醒：10-30秒热启动
- 网络延迟：2-10秒

**等待时间优化**：
- 轻量级探测：10-20秒连接超时
- 健康检查：20-30秒完整超时
- 强力唤醒：15-40秒请求超时

## ⚡ 错误处理机制

### 分层错误处理

1. **连接级别**：`--connect-timeout` 和 `--max-time`
2. **HTTP级别**：状态码检查和响应解析
3. **应用级别**：业务逻辑验证
4. **工作流级别**：`continue-on-error` 和 `if: always()`

### 常见错误场景

| 错误类型 | 处理策略 | 恢复机制 |
|----------|----------|----------|
| 连接超时 | 增加超时时间 | 重试 + 等待 |
| 404错误 | 服务在线但路由不存在 | 继续其他测试 |
| 503错误 | 服务暂时不可用 | 重试机制 |
| 网络错误 | GitHub Actions网络问题 | 继续执行后续步骤 |

### 优雅降级机制

```yaml
# 即使某些阶段失败，工作流仍继续
if: always()  # 确保阶段始终执行
continue-on-error: true  # 允许步骤失败
```

## 🛠️ 使用指南

### 基本使用

1. **自动执行**：每14分钟自动运行
2. **手动触发**：在GitHub Actions页面手动执行
3. **参数配置**：选择执行策略和调试模式

### 手动触发选项

```yaml
strategy:
  - standard    # 标准模式（推荐）
  - aggressive  # 激进模式（更多尝试）
  - minimal     # 最小模式（快速检查）

debug_mode:
  - true        # 启用详细日志
  - false       # 标准日志输出
```

### 环境变量配置

```yaml
BACKEND_URL: 'https://geo-backend-vp34.onrender.com'
HEALTH_ENDPOINT: '/api/health'
LOGIN_ENDPOINT: '/api/auth/login'
USER_AGENT: 'GEO-Production-KeepAlive/2.0'
TIMEOUT_BASE: 30
MAX_RETRIES: 5
```

### 自定义配置

**修改执行频率**：
```yaml
# 在 .github/workflows/production-backend-keepalive.yml 中修改
schedule:
  - cron: '*/14 * * * *'  # 每14分钟
  # - cron: '*/10 * * * *'  # 每10分钟
  # - cron: '0,30 * * * *'  # 每30分钟
```

**修改端点配置**：
```yaml
# 在 env 部分修改
BACKEND_URL: 'https://your-backend.onrender.com'
HEALTH_ENDPOINT: '/custom/health'
LOGIN_ENDPOINT: '/custom/auth/login'
```
